Subject: Two StandaloneBase issues found while building an AirPlay applet

Hi Sjoerd,

I'm building an AirPlay 1 receiver applet for the Squeezebox Radio/Touch,
modelled on your Spotify Connect applet. A static ARM receiver
(philippe44's libraop) serves PCM on a loopback HTTP port, and the applet
plays it through SqueezePlay's stock player with the PCM decoder. It now works
on my Radio with StandaloneBase as the only server: sound, volume from the
iPhone, Now Playing via your Now Playing API, pause/skip/stop.

While getting there I ran into two things in StandaloneBase that look worth
your attention. Details and evidence below.

Test device
- Squeezebox Radio (baby), SqueezeOS 9.0.1 r17084, kernel 2.6.26.8-rt16
- StandaloneBase as installed from your catalog (Nov 2026), player selected
  on the StandaloneBase server (127.0.0.1)
- Spotify Connect installed (not running during the tests)

------------------------------------------------------------------------
1) Recurring "connecting to StandaloneBase" screen / 402 Unknown client
------------------------------------------------------------------------

What the user sees
The Radio's screen keeps alternating between the menu and
"Connecting to StandaloneBase", even when nothing is playing. Selecting
another library (an external LMS) does not change this. My first impression
was that the Radio switched back to StandaloneBase, but it doesn't: an
external LMS still listed the Radio as connected.

Evidence (syslog, repeating every ~15-30 s)
  WARN net.comet - Comet.lua:883 Comet {StandaloneBase}: _response,
       /meta/reconnect id=nil failed: 402::Unknown client
  WARN net.comet - Comet.lua:883 Comet {StandaloneBase}: _response,
       /slim/request id=7 failed: unknown_command
  WARN applet.SlimBrowser - notify_networkOrServerNotOK() / this is a server error
  WARN applet.SlimMenus  - notify_networkOrServerNotOK

The unknown_command is the stock subscription
  ["displaystatus","subscribe:showbriefly"]
which sbbase answers with {"error":"unknown_command"} (seen in sbbase.log).

It reproduces with my AirPlay applet completely removed, so it is not caused
by it. It is worst right after a SqueezePlay restart, then settles to every
15-30 s.

Likely cause (from StandaloneBaseApplet.lua)
supervise() runs every 15 s and calls connectToLocalServer(), which calls
localServer:connect() unconditionally. The comet client then tries
/meta/reconnect with a clientId that sbbase no longer knows, gets 402, and
SqueezePlay shows the reconnect UI. The unknown displaystatus reply also
counts as a server error for SlimBrowser/SlimMenus.

Suggestions
- Only call localServer:connect() when it is not already connected (or when
  it is the selected server).
- Have sbbase answer /meta/reconnect for an unknown client with an advice to
  re-handshake (Bayeux "advice":{"reconnect":"handshake"}) rather than a bare
  402, and/or accept "displaystatus ... subscribe:showbriefly" with an empty
  reply.

------------------------------------------------------------------------
2) Sequence-number refresh storm (power/volume flood)
------------------------------------------------------------------------

What happens
When the local player plays a stream that StandaloneBase did not start
(my AirPlay applet, very likely also Spotify Connect), SqueezePlay floods
sbbase with "power 1" plus "mixer volume N" requests. I measured
29 per 10 s, and later up to 137 per 10 s. With playback idle: 0.

Evidence
sbbase.log during playback, the same pair over and over:
  COMET RX ... ["power","1",false,"seq_no:741"] ... ["mixer","volume",35] ...
  COMET RX ... ["power","1",false,"seq_no:742"] ... ["mixer","volume",35] ...
SqueezePlay debug (audio.decode):
  Playback.lua:1106 server sequence # out of sync. server: 318 local: 335
  Playback.lua:1131 setVolume: 15
  (repeating, local number increasing each time, server number stuck)

Mechanism
Player:_process_status gets a playerstatus whose seq_no is behind the local
counter, so it calls LocalPlayer:refreshLocallyMaintainedParameters(). That
re-sends volume (without seq) and power (with a new seq_no), which advances
the local counter again before the server's echo arrives. The next status is
out of sync again, and the loop repeats several times per second for as long
as the stream plays.

Side effect: the stored server volume wins
The refresh re-applies the player's stored volume, and that comes from
sbbase's "mixer volume". In my case sbbase had volume 1 stored, so every
~2 s the gain was reset to volume 1 (inaudible) whatever the source set.
That is why my AirPlay audio was silent until the knob was turned.

Your StandaloneRadio already works around exactly this in
StreamPlayer:_installHooks ("Stock Player refreshes volume/power for every
stale sequence snapshot ..."): it rebases the local sequence number to the
server's and coalesces identical refreshes. Other sources have to copy that
workaround. I did the same in my applet (own implementation).

Suggestion
Fix it once on the server side: let sbbase adopt the seq_no from the
incoming power/mixer requests (as LMS does), so its playerstatus carries the
latest local number and the player stays "in sync". Alternatively, offer the
StandaloneRadio guards as a shared helper in StandaloneBase (e.g. via
OwnershipRuntime) so third-party sources don't each re-implement them.

------------------------------------------------------------------------
Related observations (lower confidence)
------------------------------------------------------------------------
- Output-underrun resume: after an OUTPUT UNDERRUN the stock Playback pauses
  audio and waits for the server's strm-u. sbbase never sends it, so a
  third-party source stays paused forever unless it resumes locally (your
  StandaloneRadio _audioRecoveryTick does this). Another candidate for a
  shared helper, or for sbbase to send strm-u.
- Reboots: during heavy debugging the Radio rebooted several times, usually
  around "/etc/init.d/squeezeplay restart" while the storm above was
  running. The MXC hardware watchdog has a 60 s timeout. I could not capture
  the reason (/var/log/watchdog is in RAM and lost on reboot). Persisting the
  last watchdog/lifecycle reason across reboots would help diagnose this.

Happy to share logs or test a fix on my Radio, and to share the AirPlay
applet code if it's useful to you (the receiver is based on philippe44's
libraop; licence for the applet still to be decided).
